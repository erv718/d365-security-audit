Admin roles held by idle accounts

Dormant admins · Suggested owner: Identity team

What we found

  • 2 directory-role assignment(s) belong to accounts idle for 90+ days: Global Administrator: stale.admin@t.test; Global Administrator: sprayed.admin@t.test. For each: if it is an emergency-access (break-glass) account, keep it but test its sign-in at least every 90 days and alert on any use; otherwise remove the role or disable the account.

Why it matters

These accounts hold directory roles (admin roles in Entra ID) but have not signed in for 90 days or more. If one of their passwords leaks, an attacker gets admin power, and nobody is using the account to notice.

What to do

  1. Check first: find out if each account is a break-glass account (spare emergency admin account). If it is, keep it. These should be tested at least every 90 days, so this finding means the test is overdue: tell your security team, then sign in with it now.
  2. Set an alert on every sign-in by a break-glass account. This needs sign-in logs sent to a Log Analytics workspace (a store for log data).
  3. For every other account, ask the person or team that owns it whether the role is still needed. If a script or service uses the account, confirm that before you change anything.
  4. Remove each role that is not needed. If the person has left or the account is unused, block its sign-in as well.
  5. With Entra ID P2 or Entra ID Governance, use PIM (time-limited admin access), including its access reviews (scheduled checks of who has access) of admin roles, so unused roles are caught on a schedule.

Apps with powerful tenant-wide permissions

App access · Suggested owner: Identity team · 2 findings

What we found

  • 2 app(s) hold Mail.Send (tenant-wide: every mailbox unless scoped with RBAC for Applications in Exchange Online): Mail Robot, No Owner App
  • 1 app(s) hold Mail.Read (tenant-wide: every mailbox unless scoped with RBAC for Applications in Exchange Online): Mail Robot

Why it matters

These apps can act on their own, with no user signed in, across the whole tenant (your organization's Entra ID directory) or every mailbox. Some can read or send mail as anyone, change any file or site, or give themselves more rights. Anyone who steals an app's secret or certificate (its sign-in keys) gets the same power, and MFA (a second sign-in check) does not apply to apps.

What to do

  1. Check first: for each app, find its owner and what it does. Removing a permission the app still uses will break it, so agree on each change with the owner and test it.
  2. Review each app's grants at Entra ID > Enterprise apps > All applications > select the app > Permissions > Admin consent tab (approval that covers everyone). Remove what is not needed: open the menu (...) next to the permission and select Revoke permission.
  3. Ask for a narrower permission where one exists. For example, Sites.Selected (only the sites you pick) can replace Sites.FullControl.All or Files.ReadWrite.All.
  4. For mail permissions, limit each app to the mailboxes it needs with RBAC for Applications (an Exchange Online mailbox limit). Then remove the matching tenant-wide permission in Entra ID: the two add up, so the limit does nothing while it stays. The older application access policies also limit Entra permissions, but they are being replaced.
  5. full_access_as_app works through EWS (an older way apps reach mail). Exchange Online starts turning EWS off in October 2026 and fully turns it off in April 2027, so move these apps to the Graph API (the newer way apps reach data).
  6. Exchange.ManageAsApp lets an app run Exchange admin commands. What it can change depends on the admin role the app was given, so review that role as well.

Gaps in MFA coverage for sign-ins

Conditional Access · Suggested owner: Identity team

What we found

  • 0 CA policies; 0 enabled; 0 enabled policies require MFA.

Why it matters

MFA (a second sign-in check) stops most attacks that use a stolen or guessed password. If MFA is not required for every user on every app, one leaked password can open Dynamics 365, email and files. A rule that covers only a small pilot group or one app, or that leaves many people out, leaves the rest open.

What to do

  1. Check first: list every enabled Conditional Access policy (a sign-in rule in Entra ID) and who or what each one leaves out. Keep two break-glass accounts (spare emergency admin accounts) out of MFA rules, so one mistake cannot lock out every admin.
  2. Conditional Access needs an Entra ID P1 license. Without P1, turn on security defaults (free built-in sign-in protections) at Entra ID > Overview > Properties > Manage security defaults. They make everyone register for MFA, always ask admins for it, and ask other users when needed.
  3. With P1, go to Entra ID > Conditional Access > Policies > New policy. Include All users. Exclude only the break-glass accounts, plus the Directory Synchronization Accounts role if you sync accounts from on-premises Active Directory. Under Target resources, include All resources. Under Grant, select Require authentication strength, then Multifactor authentication strength. If you use an outside MFA provider, select Require multifactor authentication instead.
  4. Set Enable policy to Report-only (logs results, blocks nothing) first, and tell users so they can register an MFA method. When the results look right, switch it to On.
  5. Open each policy that already asks for MFA. If it offers MFA as one choice among others (Require one of the selected controls), people can pass it without MFA, for example from a compliant device (one that meets company rules).
  6. If a policy already covers all users and all resources, review who it leaves out. Keep only break-glass and sync accounts excluded, unless another policy covers those people with MFA.

Enabled accounts unused for 90 days or more

Dormant accounts · Suggested owner: Identity team

What we found

  • 5 of 14 enabled account(s) have not signed in for 90+ days (1 with no successful sign-in recorded since Microsoft began recording them in December 2023, 1 guest(s)). Disable or review them: they keep their access until someone does.

Why it matters

An account that nobody uses still works. If its password leaks or is guessed, an attacker can sign in, and no one is around to notice. Guest accounts (accounts for outside people) usually sign in through their own organization, so a forgotten guest keeps working for as long as that home account does.

What to do

  1. Check first: some accounts never sign in on purpose. Shared mailbox accounts (mailboxes several people use) should be blocked from sign-in, not deleted. Keep break-glass accounts (spare emergency admin accounts), and confirm service accounts (accounts used by programs) with their owners.
  2. Send the list to managers or team owners. Ask: does this person still work here, and do they still need this account? Allow for long leave. For guests, ask the team that invited them.
  3. Block sign-in on accounts nobody claims: Entra ID > Users > All users > select the user > Account status > Edit, clear Account enabled, then Save. For accounts synced from on-premises Active Directory, disable them in Active Directory first.
  4. Delete an account only after a second review and an agreed waiting period with sign-in blocked.
  5. To repeat this on a schedule, access reviews (scheduled checks of who has access) of inactive users need Entra ID Governance.

Owners of powerful apps can act as the app

App access · Suggested owner: Identity team

What we found

  • 1 app(s) that hold one of the permissions above have owners, and an owner can add a new secret and sign in as the app with no admin role: Mail Robot (Mail.Read, Mail.Send) owned by alice@contoso.test.

Why it matters

An app owner (a person who manages the app) can add a new secret (an app password) and then sign in as the app. That gives them all of the app's permissions, such as reading every mailbox, without any admin role. If an owner's account is taken over, the attacker gets the same power.

What to do

  1. Check first: ask each app's team who maintains the app and who renews its secret today. Agree who keeps that job before you remove anyone.
  2. Remove owners who have left, changed jobs, or no longer work on the app. Keep a short list of named people; two is a good minimum, so the app is never left without an owner.
  3. Check both owner lists: Entra ID > Enterprise apps > All applications > select the app > Owners, and the app's own owner list in App registrations.
  4. Treat the remaining owners like admins of that app: make sure they sign in with MFA (a second sign-in check), and include them when you review admin access.
  5. Look at each app's Certificates & secrets page in App registrations for entries nobody can explain. Ask the app team before you remove any of them.

Admin roles · Suggested owner: Identity team

What we found

Why it matters

Global Administrator can change almost every admin setting in Entra ID and the connected cloud services, and can raise its own access to read data. Allow list open to the entire internet

Network · Suggested owner: Azure team · 4 findings

What we found

  • Dataverse environment 'testx' IP firewall allows the entire internet (0.0.0.0-255.255.255.255): 0.0.0.0/0.
  • Logic App 'la-ips' accepts calls from the entire internet (0.0.0.0-255.255.255.255): 0.0.0.0-255.255.255.255.
  • SQL server 'sql1' firewall allows the entire internet (0.0.0.0-255.255.255.255): everyone.
  • SQL server 'sql1' firewall allows the entire internet (0.0.0.0-255.255.255.255): everyone.

Why it matters

This resource's allow list (addresses a firewall lets in) includes every internet address, 0.0.0.0 to 255.255.255.255, so the firewall filters nothing. Only the sign-in, key or token is left, and anyone can keep trying. Microsoft's network best practices say not to create allow rules this broad, because they give a false sense of security and are often found and exploited.

What to do

  1. Check first: find out why the rule exists and what connects through it, such as apps, reports, data tools, Microsoft services or partners. Ask the resource owner whether it was added while troubleshooting; Microsoft advises that troubleshooting procedures should ban rules like this.
  2. Where the service has an audit-only mode, as the IP firewall of Dataverse (Power Platform's data store) does, use it first to see which addresses really connect.
  3. Replace the rule with the exact ranges that need access: your office and VPN outbound ranges, plus the published ranges of any service that must connect. Where the service supports it, use a private endpoint (a private address in your network) instead.
  4. Remove the open rule and test every app that used it. The page linked for this resource type shows where its allow list is edited.

Internet-facing VM has no network security group

Network · Suggested owner: Azure team

What we found

  • 1 VM(s) have a public IP and no NSG on the network interface or its subnet; with a Basic SKU public IP every port the OS listens on is reachable from the internet: vm1 (20.1.2.3) (public IP SKU not read: open only if it is Basic). Basic SKU public IPs were retired on 30 September 2025; a Standard SKU public IP blocks inbound traffic until an NSG allows it.

Why it matters

This VM has a public IP address but no NSG (a set of firewall rules) on its network interface or its subnet. If the public IP is the older Basic SKU (pricing tier), every port the VM listens on is open to the internet. A Standard SKU public IP blocks inbound traffic until an NSG allows it, so the real exposure depends on the SKU, but in both cases nothing records what should be allowed.

What to do

  1. Check first: open the VM's public IP address in the Azure portal and note its SKU. Basic means every listening port can be reached now; Standard means inbound traffic is already blocked. Microsoft retired Basic SKU public IPs on September 30, 2025, so plan to upgrade any that remain. Add the NSG first, because a Standard public IP lets nothing in without one.
  2. Check first: list what must reach the VM from the internet, on which ports and from which addresses, so the new rules do not cut anyone off.
  3. Create an NSG with allow rules for only those ports and sources, then attach it to the VM's network interface or its subnet. The NSG's default rules block all other inbound internet traffic.
  4. If nothing needs to reach the VM from the internet, remove its public IP instead, once the owner agrees.

Remote admin or database port open to the internet

Network · Suggested owner: Network team · 4 findings

What we found

  • NSG 'nsg-a' rule 'rdp-any' opens port(s) 3389 (RDP) to the internet.
  • NSG 'nsg-a' rule 'sql-internet' opens port(s) 1433 (SQL Server) to the internet.
  • NSG 'nsg-a' rule 'all-range' opens all ports to the internet.
  • NSG 'nsg-orphan' rule 'ssh-any' opens port(s) 22 (SSH), 23 (Telnet), 21 (FTP) to the internet. (this NSG is not attached to any subnet or network interface)

Why it matters

An NSG (a set of firewall rules) on this VM or subnet lets any address on the internet try to connect to a remote-admin or database port. Automated tools scan the internet for these ports and keep guessing passwords, so one weak or reused password can be enough to get in. A VM taken over this way can then be used to attack other systems on your network.

What to do

  1. Check first: ask the VM owner who connects on this port and from which network. A finance and operations development VM deployed by Lifecycle Services (LCS, Microsoft's deployment portal) sits in a resource group with the same name as its LCS environment.
  2. Check first: on an LCS VM, keep the rule that lets the LCS addresses reach WinRM (Windows remote management) port 5986. LCS needs it to set up the VM and deploy packages. If 5986 is open to the internet, change its source to the LCS addresses listed on Microsoft's page instead of deleting the rule. Use the addresses for the LCS portal you sign in to, which can differ from the VM's Azure region.
  3. Change the open rule's source (Any, Internet or 0.0.0.0/0) to your office or VPN outbound range. LCS allows RDP (Remote Desktop) port 3389 from anywhere by default, and Microsoft recommends limiting it to the clients that need it. For a database port, allow only the servers that use the database. Test with a new connection afterward.
  4. To avoid a standing rule, use the company VPN (a private tunnel into your network) or Microsoft Defender for Cloud just-in-time VM access (ports opened only on request), which needs Defender for Servers Plan 2. Remove the always-open rule when you turn just-in-time access on, and on LCS VMs leave port 5986 out of its port list.
  5. Microsoft's LCS security page names Azure Bastion (browser-based remote access) as an option for RDP, but Microsoft's LCS FAQ says Bastion has not been tested or supported with cloud-hosted environments. Treat Bastion as unsupported for LCS VMs.
  6. If the finding says the NSG is not attached to anything, the rule has no effect today but applies as soon as someone attaches the NSG. Fix the rule now, or delete the unused NSG after its owner confirms it is not needed.
